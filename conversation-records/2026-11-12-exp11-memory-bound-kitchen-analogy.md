## 先认识 GPU 的两个部件：仓库和后厨

把 4090 想象成一家餐厅：

| GPU 部件 | 餐厅角色 | 本钱 |
|---|---|---|
| 显存 | **仓库**（存放 3GB 模型权重） | 存得下 |
| 显存带宽 | 仓库到后厨的**传送带** | 每秒约 1TB |
| 计算单元（几千个核心） | **后厨的灶眼** | 每秒约 80 万亿次乘加，极快 |

关键点：**灶眼再快，食材不运到就开不了火**。生成一个 token 需要的每一次乘法，都要先把对应的权重从仓库搬到后厨。

## 每生成 1 个 token，GPU 实际在干什么

模型有 1.5B 个参数（bf16 下 3GB）。**每生成 1 个 token，都要把全部 3GB 权重从头到尾用一遍** —— 28 层，每层的每个矩阵都要参与计算。

于是每一解码步的工序是：

```
传送带把 3GB 权重从仓库搬到后厨  →  灶眼拿这些权重做一点点乘法  →  得出 1 个 token
        （耗时的大头）                    （耗时的小头）
```

量级感受（粗略，别当精确值）：搬 3GB 的时间是“毫秒级”，而 1 个 token 所需的乘法对 4090 来说只要“零点零几毫秒”。**灶眼 99% 的时间在等食材，闲着。**

这就叫“访存主导”（memory-bound）：**瓶颈是搬食材，不是炒菜。**

## 现在回答核心问题：为什么“无缓存重算”不要钱？

无缓存 = 每步要把前面 172 个 token 的账**全部重算一遍**。直觉上这应该慢 172 倍啊？—— 不会，因为一个反直觉的数学事实：

> **矩阵乘法中，权重只需要搬一次，就能服务所有 token 的计算。**

具体说：一层的前向是 `172 个 token 的激活 × 同一个权重矩阵`。这个权重矩阵**从仓库搬进来一次**，放在后厨案板上，就可以被 172 行激活**反复使用**。搬运量和 token 数无关，只有计算量随 token 数增长。

回到厨房：

| | 有缓存 | 无缓存 |
|---|---|---|
| 传送带（搬运） | 搬 3GB 权重（做 1 道菜） | **还是搬同样的 3GB**（同一批食材在案板上切配 172 次） |
| 灶眼（计算） | 开工 0.1% | 开工 2% —— 反正本来就闲着 |
| **耗时** | ≈ 传送带时间 | ≈ **还是传送带时间** |

**多算的 171 份账，全部塞进了灶眼原本闲置的时间里 —— 所以免费。** 两组每步都付同样的“3GB 搬运费”，时间自然一样（0.998x）。

## 用你自己的数据交叉验证（两个独立证据）

1. **时间一样**：18.7ms/token，两组分毫不差 —— 符合“瓶颈是同一趟传送带”；
2. **显存峰值几乎一样**（2.894 vs 2.896 GiB）：如果重算需要“更多的搬运或更多的存储”，峰值应该明显变化 —— 没有，因为额外发生的只是计算，不是数据移动。

## 那什么时候无缓存会变慢？—— 菜多到灶眼忙不过来的时候

免费是有条件的：**切配量必须塞得进灶眼的空闲时间**。两种情况会击穿这个条件：

1. **菜谱太大（模型变大）**：比如 70B 模型，140GB 权重。传送带要跑更久（140GB），同时每步重算的计算量也大 46 倍 —— 灶眼空闲时间被填满后，重算开始**额外**占时间，缓存优势显现；
2. **菜的道数太多（序列变长）**：172 道 → 2000 道，切配量线性上涨，总有一刻超过灶眼空闲容量；而且注意力计算还有 O(L²) 的额外税。

你实验 10b 在 ~430 步时已经看到方向（x1.34），实验 11 在 128 步看不到 —— **转折点在两者之间，具体在哪，就是实验 12 可以量出来的东西**。

---

一句话总结：**这台 GPU 上这个小模型的每一步，时间都花在“把菜谱从仓库搬进后厨”上，炒菜本身几乎是白送的；无缓存只是多炒了几道菜，没多搬一趟食材 —— 所以不收钱。**
