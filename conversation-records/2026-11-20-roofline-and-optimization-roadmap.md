## 单卡 4090 + Q4_K_S 的输出上限

**① 显存预算**(4090 共 24564 MiB):

```
权重(Q4_K_S)      20,893,015,008 B ≈ 19,920 MiB
─────────────────────────────────────────────
剩余                4,644 MiB
− 运行时缓冲(CUDA上下文/计算图/临时张量) ≈ 1,300 MiB
− DeltaNet 恒定状态(30层 × 2MiB)          ≈ 60 MiB
─────────────────────────────────────────────
可用于 KV cache     ≈ 3,300 MiB
```

**② KV cache 能装多少 token**(混合架构每 token 仅 20 KiB):

```
3,300 MiB × 1024 ÷ 20 KiB/token ≈ 169,000 tokens
```

**③ 三重上限取最小：**

| 约束 | 上限 |
|---|---|
| 模型原生窗口(config 写死) | 262,144 |
| **单卡 Q4_K_S 显存** | **≈ 16.5 万 ← 卡在这里** |
| 输出 = 窗口 − 输入 | 16.5 万 − prompt |

## 结论

- **理论最大输出 ≈ 16 万 tokens**(prompt 极小时)，瓶颈是显存而不是模型窗口
- **实际部署建议 `-c 131072`(13 万)**：留足余量更稳，此时单次最大输出 = 131,072 − 输入 token 数；按 50~90 tok/s,一口气生成满 13 万 token 约 **25~45 分钟**
- 想在单卡上逼近模型原生的 26.2 万上限：换 `UD-IQ4_XS`(17.7G,省出 3G 显存 ≈ 15 万 KV 空间，质量略降一档)，那个文件之前列过，要的话我下

## 【提问】也就是说 每秒最多输出多少token呢

**【回答】**

单卡 Q4_K_S 的速度上限，还是那个公式——**理论屋顶 = 显存带宽 ÷ 每 token 激活权重的读取量**：

## 理论计算

```
单卡 4090 带宽:1008 GB/s
Q4_K_S 平均 ~4.5 bit/权重 → 激活 3B × 0.56 字节 ≈ 1.7 GB / token

理论解码上限 = 1008 ÷ 1.7 ≈ 600 tok/s   ← 物理屋顶,永远达不到
```

## 现实折扣(为什么达不到 600)

batch=1 单流解码是**延迟敏感型**的，每 token 要跑 40 层 kernel:MoE 专家分发、DeltaNet 扫描、Q4 反量化、kernel 启动开销……在 llama.cpp 上这些通常吃掉 85~90% 的屋顶。

| 场景 | 速度 |
|---|---|
| **单流输出(llama.cpp,flash-attn,全层上卡)** | **50~90 tok/s** ← 你日常体感的数字 |
| + 投机解码(MTP/自草案) | ×1.5~2 → 100~150 tok/s |
| 多人并发(带宽复用，如组内 3-4 人同时用) | 聚合 200~400 tok/s |

## 把三个答案串起来(单卡 Q4_K_S 全景)

| 指标 | 数值 |
|---|---|
| 一次最多输出 | ~13 万 tokens(建议 `-c 131072`) |
| 每秒最多输出 | 实际 **50~90 tok/s**(理论屋顶 600) |
| 跑满一次输出的耗时 | 25~45 分钟 |

这些都是纸面推算——llama.cpp 装好后跑一次 `llama-bench` 十分钟就能拿到真实数字。要现在装吗？

**【回答】**

明白，给你一份可以直接当优化基准用的**逐项 Roofline 模型**。所有数字基于 `config.json` 的架构参数推导，你可以逐项验证。

## 一、每生成 1 个 token,到底要读多少字节

**① 激活参数明细**(MoE 每 token 只动这些):

| 组件 | 计算 | 参数量 |
|---|---|---|
| MoE 专家(40 层 × (8 路由 + 1 共享) × 3×2048×512) | 40 × 28.3M | **1.154B** |
| 路由器(40 × 2048×256) | 40 × 0.52M | 0.021B |
| Gated Attention(10 层：Q/K/V/O/门控) | 10 × 27.3M | 0.273B |
| Gated DeltaNet(30 层:Q/K/V/Out) | 30 × 25.2M | 0.755B |
| LM Head(248320×2048,每 token 必读) | — | **0.509B** |
| **合计激活** | | **≈ 2.69B**(与官方"3B 激活"吻合) |

**② 每 token 显存流量模型**(单位 GB,bus 宽 1008 GB/s):

```
T(N) = W + S + kv(N)

W = 激活权重字节 = 2.69e9 × (4.8 bit ÷ 8)   ≈ 1.61 GB   ← Q4_K_S 实测平均 4.8 bpw
S  = DeltaNet 状态读写 = 30层 × 2MiB × 2(fp32, 读+写) ≈ 0.13 GB(与 N 无关)
kv(N) = KV cache 读取 = 20,480 B × N        ← 只有 10 层全注意力,每位置 20 KiB
         (20,480 = 10层 × 2(K,V) × 2头 × 256维 × 2B)
```

## 二、理论速度上限 = 1008 ÷ T(N)

| 上下文 N | T(N) | **带宽屋顶** | 计算力屋顶(FLOPs) |
|---|---|---|---|
| → 0(短上下文) | 1.74 GB | **580 tok/s** | ~30,000(不构成瓶颈) |
| 32K | 2.41 GB | 418 tok/s | ~15,000 |
| 64K | 3.08 GB | 327 tok/s | ~8,000 |
| 128K | 4.42 GB | **228 tok/s** | ~5,900 |
| 262K(满窗口) | 7.11 GB | 142 tok/s | ~3,100 |

**关键结论**:
1. **全程带宽瓶颈**，计算力在所有上下文长度下都有 20~50 倍余量——优化方向只有一个：砍字节数、提带宽利用率
2. **拐点在 N≈78K**:KV 读取量(20480×N)在 78K 处追平权重读取(1.74G)。超过 78K 后，你的优化主战场从“专家权重搬运”变成 **KV cache 带宽**——这是混合架构在超长上下文下的隐藏代价
3. 工程上限：kernel 启动、访存依赖链决定 100% 屋顶不可达，**现实的优化天花板 ≈ 屋顶的 50~60%**,即短上下文 ~300 tok/s、128K ~120 tok/s

## 三、每个优化杠杆砍的是哪一项

| 杠杆 | 作用项 | 收益 |
|---|---|---|
| KV cache 量化 FP8/INT8 | kv: 20480→10240 B/pos | 128K 处 T 4.42→3.05,**屋顶 228→330** |
| DeltaNet 状态 bf16 | S: 0.13→0.065 | 短上下文 +4% |
| 融合 MoE 反量化 kernel(减少专家权重二次搬运) | 提高 W 项带宽利用率 | 直接提升达成率 |
| **MTP 投机解码(接受长度 k)** | 整个 T(N) 摊到 k 个 token | **近似 ×k,是最强杠杆**(权重只读一次出 k 个 token) |
| batch 并发 | W 摊到 b 条序列 | 聚合吞吐近线性 ↑,直到 KV 带宽饱和 |
| 换 IQ4_XS(4.2 bpw) | W: 1.61→1.41 | 屋顶 +14%,代价是反量化更复杂 |

**验证建议**：llama.cpp 装好后跑 `llama-bench -p 0 -n 128`(纯解码)，对照上表“带宽屋顶”算达成率——目前 llama.cpp 对这类混合 MoE 一般只能到屋顶的 8~15%(50~90 tok/s),你和 580 之间的差距就是你的优化空间。

## 两次运行对比给你的优化路线图

| 配置 | 短上下文屋顶 | 128K 屋顶 | 显存可容上下文 |
|---|---|---|---|
| 当前(Q4_K_S + BF16 KV) | 579 | 228 | 16.1 万 |

三个量化结论，供你排优化优先级：

1. **KV FP8 是长上下文第一杠杆**：每位置字节 20→10 KiB,128K 屋顶直接 +53%,还附带把显存可容上下文从 16 万拉到 65 万(瓶颈从此变回模型原生 26.2 万窗口)

`@10%/25%/50%` 三列是你实测数字的对标线：llama-bench 测出来除以屋顶就是达成率，达成率不涨说明瓶颈不在这三项流量里(去看 kernel 启动开销/同步点)。

## 【提问】你现在看看 如何进行算子优化吧

**【回答】**

环境摸清了，这很关键——你的栈是 **PyTorch 2.5.1 + Triton 3.1.0,4090 单卡**(没有 nvcc,但 Triton 自带编译链，不装 CUDA toolkit 也能写 kernel);你的 infra 仓库是“每次只改一处”的受控实验方法论。算子优化方案我按**能直接落成 experiment-12+ 系列**的方式给你。

## 一、优化对象：解码一步的热路径

接你的 experiment-09 手写解码循环，每 token 的算子清单(按流量排)：

| 算子 | 流量占比(短上下文) | 病灶 |
|---|---|---|
| MoE 专家 GEMV(40 层 × 9 专家) | ~92%(W=1.61G) | 带宽型；权重布局不连续、dequant 与 GEMV 分离 |
| DeltaNet 扫描(30 层) | ~7%(S=0.13G) | 时序依赖，逐 chunk 串行；状态 fp32 读写 |
| GQA 注意力(10 层) | N<8.5 万时小 | N>拐点后反超权重，KV 带宽型 |
| Router/Norm/激活/采样 | 字节少 | **kernel 数量多 → launch 开销型**(decode 每步 40 层 × 十几个小 kernel,上千次 launch) |

## 二、方法论：先测后改，三板斧

**第 0 步永远是解剖现状**(不装 Nsight 也行，torch.profiler 够用)：

```python
from torch.profiler import profile, ProfilerActivity
with profile(activities=[ProfilerActivity.CPU, ProfilerActivity.CUDA]) as prof:
    decode_step()          # 你 exp-09 的循环体
print(prof.key_averages().table(sort_by="cuda_time_total", row_limit=20))
# 看三样东西:① kernel 间空隙(=launch/同步开销) ② 大 kernel 的 DRAM 带宽利用率
# ③ 小 kernel 的数量(融合候选)
```

然后按病灶选斧头：**融合**(elementwise 链合成一个 kernel)、**合并访存**(coalesced load,让 DRAM 利用率逼近峰值)、**消同步**(去 D2H、去每步 `.item()`)。

## 三、实验路线(延续你的受控 A/B 风格)

| 编号 | 改动(只改一处) | 度量 | 预期 |
|---|---|---|---|
| **exp-12** | `torch.profiler` 解剖手写 decode,按 kernel/空隙/带宽分类耗时 | 时间分解表 + DRAM 利用率 | 建立 baseline 认知 |
| **exp-13** | `torch.cuda.CUDAGraph` 捕获整个 decode step | TPOT A/B | 小 batch 下 **-20~40%**(杀上千次 launch) |
| **exp-14** | Triton 融合 `RMSNorm+残差加`(或 top-k 采样链) | 单算子延迟 A/B | 首刀练手：小 kernel 融合收益 |
| **exp-15** | Triton 手写 bf16 GEMV vs `torch.matmul`(batch=1) | 达成带宽 % | 学到 GEMV 怎么吃满带宽(目标 >80% 峰值) |
| **exp-16** | GQA 注意力：手写 Triton kernel vs `SDPA` | N 扫描(4K→128K) | 看清 KV 带宽拐点，验证 roofline 模型 |
| **exp-17** | MoE grouped GEMV:专家权重连续布局 + topk 分发融合 | 专家利用率/带宽 | 最难也最值钱的一仗 |
| **exp-18** | KV FP8 存储对 exp-16 kernel 的影响 | 长上下文 TPOT | 验证 +53% 的纸面推算 |

每个实验都拿 `roofline.py` 的对应档位算**达成率**，这样每一步优化都有理论对标——这正是你仓库一直在做的事。
